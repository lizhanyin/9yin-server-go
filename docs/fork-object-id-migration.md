## 一、问题：为什么冲锋/移动/接近全部失效

fork 客户端的**移动/接近子系统按对象 id 的高位类型位校验对象**。我们
的 id 方案（玩家=1/1、NPC=裸小 id）下：

| 子系统 | 表现 |
|---|---|
| 渲染 / 选中 / 伤害 / 买卖 / 对话 | 正常（这些系统把 id 当哈希键） |
| 客户端自主接近（官服客户端按键即走） | **从不武装**（298→209 授权拿了也不走，连要 12 次） |
| c61 冲刺指令 / 0x20 ServerMoving / 0x21 ServerAllDest | **对玩家对象全无视**（2026-11-08 夜两轮实证） |
| 0x1F ServerLocation 位置锚 | **生效**（宽松校验 → 表现为"瞬移"） |

即：服务端所有"让客户端动起来"的帧型都被 id 校验挡住，唯一穿透的
0x1F 只能瞬移。**这是冲锋接近段、轻功服务端驱动、一切服务端位移的
共同根因。**

## 二、证据链（全部可复核）

### 2.1 参考服 ground truth（fork 家族服务端 + 同款客户端真机会话）

位置：`F:\Game\Online\9yin\9yin_server1\captures\local\`
（49840 / 50504 / 62311 / 64596 四组 c2s/s2c bin 对）

从 **49840**（含完整登录）解码：

1. **玩家自体 id 首次出现于 0x0B PlayerEntry（81B）**：
   `[0b][seq u32][obj=0x11000001][owner=0x7a5c0b][04 00][24 00][场景串][08 00 "born03"]`
   —— 客户端从 0x0B 学到自己的 (obj, owner)，之后所有自体帧
   （0x10 属性 / 0x28 / 0x1F）统一用这对 id。
2. **NPC id = `0x11000000 | 索引`**：0x0D 物化块 obj ∈ {0x1100004b,
   0x1100004e…0x11000051, 0x1100036a…}，owner 恒 1。
3. **客户端自己的 298 请求目标是 obj(0x11000995, 1)** —— 同方案。
4. owner=0x7a5c0b ≈ 801 万，**疑为 DB 角色 id**（我们测试角色 role=618，
   量级不符但语义吻合"每角色唯一"）。未最终钉死，见 §五-3。

### 2.2 单改 obj 的失败实验（51357 会话，2026-11-09 00:30）

仅把 `playerObjectID` 常量改为 0x11000001（owner 仍 1）：

- 0x0B 帧内 id 已正确携带新值（常量自动流入）
- 客户端收到完整进世界链后 **10 秒无 ClientReady → 重发 0x04 选角 →
  被 FSM 拒（0x04 in entering_world）→ 断连**

结论：客户端对 (obj, owner) **成对校验**——obj 换成 0x11 系而 owner
仍是 1，配对不合法即判定进世界失败。**迁移必须 obj/owner/账号层一次
到位，不能分步。** 已回滚恢复基线。

### 2.3 官服对照组（证明这不是"官方协议"差异；2026-11-09 补全量 id 表）

官服（a/b/c/e/f/g.pcapng）对象 id 是另一套（0x0700xxxx + owner 0x0499xxx），
且官方客户端**本地实现**按键即走（服务端零参与）。fork 客户端没有该
本地行为，只能靠服务端驱动，而驱动被 id 校验挡住 —— 两条证据合流
指向 fork 自有 id 方案。

**官服实体 id 全量提取**（聚合六份抓包的全部 0x10 帧头 + 0x0D 物化 +
0x1F 锚；官服视口稀薄，全程仅 11 实体；d.pcapng 在 7074 口无流量为空；
解码脚本逻辑：FrameDecoder 逐帧取 op 0x10 的 obj@[2:6]/owner@[6:10]）：

| id | owner | 身份 |
|---|---|---|
| 0x0700014b / 0x07000152 / 0x07000157 | 0x150 / 0x157 / 0x15c | NPC（低 24 位=331/338/343 **连续小号**） |
| 0x070067ff | 0x3b04af | NPC（b 会话冲锋目标） |
| 0x0700ca8c | 0x3b6fb8 | **玩家**（a+b 会话同一人、同 owner） |
| 0x07020e3a / 0x07020fa4 | 0x3b0a93 / 0x3b3cc3 | NPC / 玩家（c2 会话） |
| 0x07033e09 / 0x07036540 | 0x3b0a8e / 0x3b04aa | NPC |
| 0x07034e9b | 0x498afc | 玩家（g 会话） |
| 2 / 28（无 0x07 前缀） | 行号 | 视图行（View40 等，独立体系） |

官服生成规律：
1. **obj = `0x0700_0000 | 场景内顺序索引`**——0x700014b/152/157 三连号
   （331→343）铁证，与我们的"目录下标+2"同构；
2. **玩家同用 0x07 段**（无特殊段位），owner 为会话/实例令牌（同玩家
   跨会话 a=b 同 owner 0x3b6fb8，不同玩家不同号）；
3. **NPC owner = 每实例/批次号**（量级混杂：0x150 小号与 0x3b04xx
   大号并存，按出生批次分配）。

**对迁移的意义**：官服 0x07 方案与参考服 0x11 方案是**同一架构**
（类型前缀 + 场景索引 + 实例 owner）——与"我们缺前缀所以移动全灭"
三重互证。但 **fork 客户端校验的是 0x11 系**（49840 实证），迁移目标
段维持 0x11000000 不变，官服 0x07 不采用。官服"玩家 owner=会话令牌"
与参考服 0x7a5c0b 的关系是阶段 0 owner 语义钉死时的旁证（倾向：
owner 只要每角色/会话唯一即可，客户端只验配对合法性不验取值规则）。

## 三、现行实现（迁移前的事实基线）

- `player_actor.go`：`playerObjectID=1 / playerOwnerID=1`（常量，贯穿
  全部自体帧：0x0B/0x0D/0x10/0x1F/24/337/19/205/169/记录表……）
- `scene_run.go:63-77`：**自体 1-1 是流内相对 id**；远程玩家由
  `attachMember` 分配**会话内唯一 wireID**（`nextWireID = len(catalog)+2`
  起自增）并 `materializeMemberLocked` 物化 —— 多客户端不冲突，但
  wireID 不稳定（重进场景变号）、owner 共享 1。
- NPC：`registerNPCLocked(uint32(index)+2, …)` 裸小 id；宝箱/掉落物
  另有 `loot_box.go:207 nextWireID` 族分配。
- **多角色结论**：同账号单角色在线 = 无冲突；两客户端 = 靠流内 1-1 +
  远程唯一 wireID 成立。迁移到 (0x11 系 obj, 角色 id owner) 后全局唯一
  且跨会话稳定，多角色安全性**升级**；需补顶号闸（§五-4）。

## 四、目标方案（定稿）

```
玩家：obj = 0x11000001（首角色槽位号；若参考服证实每角色递增则按 DB 顺序分配 0x11000001+n）
      owner = 角色 DB id（我们 = role 表主键，如 618）
NPC：  obj = 0x11000000 | 索引（目录下标，保持现注册序）
      owner = 1
视图对象（0x28 视图行）：不迁移（id 语义不同，40=View40 等）
宝箱/掉落实体：若已是 ≥0x01000000 的大号 id 保持；否则并入 0x11000000 段并防撞
```

全部自体帧与远程帧的 (obj, owner) 来源统一改为：玩家走
`playerActor` 会话字段（不再用全局常量 1），NPC 走 `forkNPCID(idx)`。

### 阶段 0：钉死两个未知数（先做，半天）

1. **owner 语义**：解码 49840 的 0x02 账号包与角色列表 0x04 应答，找
   0x7a5c0b 的来源（是否等于其中某个角色/账号字段）。若拿不到，用
   双角色对照：62311/50504 若是不同角色，比对各自 0x0B 的 owner——
   不同则坐实"每角色唯一"，取值规则按其 DB id 位数推断。
2. **obj 槽位规则**：多角色会话里第二角色的 0x0B obj 是否 0x11000002。
   若参考抓包没有第二角色在线样本，按"每角色 = 0x11000001 + (role_id
   模 N)"或"恒 0x11000001 + owner 区分"二选一（倾向后者，风险最低：
   只要 (obj,owner) 对唯一即可），并在文档记录取舍。

### 阶段 1：id 供给层（与现有代码解耦）

1. `playerActor` 增 `objectID/ownerID uint32` 字段（登录时按阶段 0 规则
   填充；单机默认 0x11000001/618）。全局常量 `playerObjectID/
   playerOwnerID` **删除或降级为默认值**，所有引用改走实例字段
   （`p.wireObject()` 之类的访问器）。工作量集中在编译器驱动替换。
2. 新增 `forkNPCID(idx uint32) uint32 { return 0x11000000 | idx }`，
   `registerNPCLocked` 入口统一映射（**注意**：≥0x01000000 的既有大号
   id 直通；测试曾因裸断言 `EntityID(91)` 崩 20+ 例——测试统一改用
   `forkNPCID(91)` 字面量或 helper）。
3. 顶号闸：同 role_id 二次登录 → 踢旧连接（若账号层已有则验证即可）。

### 阶段 2：帧层与登录链对齐

1. `0x0B PlayerEntry` 构建器：obj/owner 取实例字段（51357 实验已证
   该帧是客户端自体 id 的唯一来源，值会自动跟随）。
2. 自体 0x0D / 0x10 / 0x1F / 24 / 337 / 19 / 205 / 169 / CD 记录表 /
   `writePlayerTargetLocked` 等：全部改走实例字段（大部分已经引用
   常量，改常量→字段即可自动一致）。
3. **远程玩家链**：`attachMember` 的 wireID 分配改为直接使用该成员的
   (obj, owner)（即所有客户端看到同一个稳定 id，替代会话内自增号）；
   `materializeMemberLocked` 与远程属性/中继帧同步。
4. 账号层一致性：0x02/角色列表里若携带任何对象 id 字段，与阶段 0
   结论对齐。
