# 官服 0x29 批量预载通道解析（2026-11-11）

> **结论一句话**：0x29 是登录进场簇里的**玩家记录批量预载通道**——
> `[0x14 sub0 (0,0,rec_id) 宣告] → [0x29 批量下发该记录表的行集]` 交替，
> 约 29 组把玩家全部持久化状态（任务/称号/好友/装备方案/游历/起源/副本/摊位…）
> 一次性灌入客户端。帧 = 0x27-0x30 族压缩值消息（mode=0x47 LZ），
> 明文体 = **去掉 op 字节的 0x11 记录消息**（首字节即 0x11 的 sub）：
> `[sub u8][obj u32][own u32][rec u16][flag2 u16][rows u16][行×rows]`，
> 行编码与 0x11 完全一致——按 0x0A 记录表 cols 列型定宽/变长序列化。
> c/k/l/登陆 四包 503 帧中 244 帧已解出明文（流内共享 LZ 池时序解码），
> 235 个 t=0 帧里 **139 帧走查字节级精确对齐**（含 Task_Completed 全部 112 帧）。
>
> 承接：`docs/官服模式NPC渲染收束.md` 余项 2（「0x29 全压缩，语法仍锁在 LZ
> 字典后——池种子未定位」）——本文解锁语法；池种子补充结论见 §四。

## 一、通道定位：登录流里的位置与配对

0x29 只出现在 4 个抓包：**c.pcapng ×95、k.pcapng ×211、l.pcapng ×102、登陆.pcapng ×95**
（a/b/d/e/f/g/i/j/m/技能 全零）。全部 mode=0x47（LZ 解压 + 4B 长头）。
c/k/登陆 三包是同一登录序列的独立会话——同位置帧解压明文除 obj/own 外
**逐字节一致**（跨会话恒定 ⇒ 服务端静态记录数据 + 会话对象标识）。

时间线（c.pcapng，t0+0.07s 簇内）：

```
[117] 0x0B 玩家进场
[118..122] 0x14/0x11 对（视图行宣告+单行更新）×3
[120] 0x14 sub2 (0,0,363=Count_Limit_Form_Rec) → [121?] 0x29
[122] 0x14 sub2 (0,0,365=prep_show_npc_rec)  → [123] 0x29 …
[133..259] 0x14 sub0 (0,0,rec) → 0x29  ×27 组（0x28 场景对象帧穿插其间）
```

### 0x14 宣告 → 0x29 承载配对（c.pcapng 全清单）

0x14（len=12）= `[14][sub][obj u32][own u32][tag u16]`：
- **sub0**：obj=own=0、tag=记录 id → 紧随 0x29 批量下发该记录行集（玩家态）
- **sub1**：(obj,owner,tag) → 紧随 0x11 单行更新（视图行事件）
- **sub2**：obj=own=0、tag≥361 → 0x29/0x11 全局记录形态

**0x14 的 tag ≡ 0x29 明文的 rec 字段**（20↔20、31↔31、36↔36、45↔45、
98↔98、105↔105、122↔122 逐对闭环验证）。

## 二、帧格式与明文语法

### 2.1 帧层（0x27-0x30 族压缩值消息，与 0x28 同规）

```
帧 = [op 0x29][mode 0x47][len-1 u32][outlen u32][LZ 流 @10]
mode 0x47 = bit1(4B 长头) + bit0(LZ 解压)     # 对比 0x28 v3 生成器用的 0x46=纯 memcpy
LZ 流语法 = tools/op28/lzdec.py（fxnet2 RVA 0x1000-0x1260 逆向版）
```

### 2.2 明文体 = 无 op 的 0x11 消息（首字节即 sub）

```
[sub u8][obj u32][own u32][rec u16][flag2 u16][rows u16][行 × rows]
 15B 头                                    行区（rows 条，按 cols 串行）
```

- `sub`：实测 0（记录行集，主流 235/244）与 1（串表形态，×9，见 §3.3）
- `obj/own`：玩家对象标识（与同会话 0x0B/0x10/0x11 帧一致；跨会话同帧仅此不同）
- `rec`：0x0A 记录表行号（≡0x14 宣告的 tag）
- `flag2`：实测 0x0000 / 0x8000（Task_Completed 连发系列交替）——**半区/分片标志**
- `rows`：行数（LE u16；**无位图特例**——初判"0x8000 位图模式"系字节序误读，
  527B 帧 rows=0x0080=128 纯行数，128×u32=512B 精确填满）

### 2.3 行编码（与 0x11 帧逐字节同构，双例精确验证）

行 = 记录表 `REC[rec].cols` 列型序列：

| 列型 | 宽 | 语义（实证） |
|---|---|---|
| 01 | 1B | u8 |
| 02 | 2B | u16 |
| 03 | 4B | u32 |
| 04 | 4B | f32 |
| 05 | 8B | f64 |
| 07 | 变长 | 串：[len u32 含NUL][GBK+NUL] |
| 08 | 变长 | 串变体（LiuYanNotes/StallNotes 用，含 NUL 填充态） |
| 06/09 | ? | 未单独实证 |

精确对齐样例（跨四包字节级一致）：
- SanHillRec（cols=020102010222→六列 10B/行）：30×10+15=**315** ✓
- Origin_Active（cols=03）：114×4+15=**471** ✓（全 0=未激活列表）
- title_rec（cols=030104→9B/行）：128×9+15=1167+**512B 尾区**=1679
- Task_Completed（cols=03）：128×4+15=**527** ✓（112 帧全精确；任务状态 u32 字）
- 0x11 侧同构验证：rec=17 JHTour_Record 2 行=16+63=**79** ✓、
  rec=31 29 行=16+116=**132** ✓ ⇒ **0x11 头仅比 0x29 明文头多 [op][sub] 两字节中
  op 由外层帧承担，0x11 自身 16B 头 = 2B(op,sub)+14B**，行区规则完全一致

### 2.4 行内增量串编码（开放，已有实证样本）

JHTour_Prize 行2 串 = `00×5 "be" 00×3 "an" 00`（13B）——NUL 槽为**回引**：
`[回引5B="tour_"]+"be"+[回引3B="iyu"]+"an"` ⇒ **tour_beiyuan**
（行1=tour_xiyu，回引源=前一行同列串）。DongHaiHomePointList 行含
"penglai"、尾区含 "chunyiguan"/"longdao?" 同类 NUL 包裹串。
⇒ 官方在行级对串列做了前缀复用压缩；len 槽内 NUL 段=回引用量。
**走查器目前把 NUL 原样输出**，此项是 96 帧未精确对齐的主因之一。

## 三、解码战况与形态统计

| 包 | 0x29 总数 | 独立 World | 流内共享池 |
|---|---|---|---|
| c.pcapng | 95 | 7 | 44 |
| k.pcapng | 211 | – | 116 |
| l.pcapng | 102 | – | 46 |
| 登陆.pcapng | 95 | – | 38 |
| 合计 | 503 | – | **244** |

- 明文头 9 字节 `[00][obj][own]` 的 obj 分布：玩家自身（0x07020fa4 等）43 帧 +
  各会话记录容器对象（0x70754e3/0xe0165cb 等）192 帧；t=1 串表 9 帧。
- **t=0 走查（四包合计 235 帧）：139 精确 / 96 带尾区或增量串**。
  尾区尺寸跨包恒定（111/136/48/85/160B…）⇒ 真实结构非解码噪声。
- **t=1 形态**（×9，头 `[01][u32 如0x74/0xa1][u32 1][u32 如0xa7][u16 10][串区]`）：
  内容为 gemskill_052 / sh_ys 等技能、生活串 + 数字段（56/57/43/52）——
  疑为「id→串」映射表形态（对应 0x11 sub1 视图行语义），未完全走查。

### 3.1 LZ 池种子结论（对 NPC 渲染收束 §余项2 的回答）

1. **池不跨连接**：k（11 流）/l（15 流）全流按时间序共养一个 World，
   ok 数与逐流独立完全相同 ⇒ 每连接独立字典状态。
2. **种子在本连接内、非 0x27-0x30 族**：首条 0x27（帧 111）即 17/24 fail ⇒
   池在登录更早期已被别的东西注册。
3. **候选源命中**：miss 槽 idx（如 0xd2d/0x26e/0x352/0x132）多数能在
   **0x09 属性表原始帧 / op32 票据 / 0x29 前小帧（0x0B/0x10/0x11/0x14/0x1E）
   的 4B 滑窗**里找到哈希注册位 ⇒「表内容参与」方向部分成立（但注册机制
   不是"表帧走 LZ 解压器"——0x09/0x0A 是明文表帧，mode 字段与 0x27 族无关）。
4. **存在本地种子（实锤）**：miss 槽 0xc1f、0x8bc 在 c.pcapng **全部捕获字节**
   中无任何 4B 滑窗可注册 ⇒ 池含客户端本地初始状态（fxnet2 .data 静态填充
   或握手/密钥派生数据），单靠抓包无法完整重建。
   ⇒ **重放路线放弃 LZ 池精确重建，走 0x46 明文路径**（官方 l.pcapng 自有先例）
   是唯一工程可行解——与 0x28 v3 的结论殊途同归。

## 四、对本服实现的意义（fork / 官方方言）

1. **fork 场景 0x29 非必需**：fork 客户端记录状态可全走 0x11 单行明文更新
   （我方现状），0x29 缺席不影响登录与渲染（真机已证）。
2. **真·官服还原（official2433 无头块）**：若需镜像官服登录序列，0x29 可用
   **mode=0x46 纯 memcpy 明文帧**构造（绕开 LZ 池/种子依赖）：
   - 帧：`[29][46][len-1 u32][明文体长 u32][明文体]`
   - 明文体：`[00][obj][own][rec u16][flag2=0][rows u16][行×rows]`
   - 行按 `internal/clientdata/official_record_table.bin` 的 cols 列型序列化，
     串列 `[len u32 含NUL][GBK+NUL]`；**无需实现行级增量串编码**（明文路径
     直接写全串即可，len 与内容一致）
   - 配对：每帧前发 0x14 sub0 `[14][00][0][0][rec u16]`
3. **记录表服务端资产**：`official_record_table.bin`（447 条含列型）已可驱动
   生成；0x29 预载清单（§一表）即官服登录时服务端认为需要下发的记录全集，
   可按此顺序镜像。
