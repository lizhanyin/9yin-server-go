# 官服登录帧对照与缺口清单（c.pcapng ↔ protocol-probe）

> 基准：`docs/official/官服抓包交互时间线分析.md` 及三份附录（a–i.pcapng，2026-11-08 抓取）。
> 登录样本为 **c.pcapng**（会话①断线重连，唯一带完整握手的段：C2S op04 → 全量快照 → ClientReady → 技能大簇 → 进场物化，0–7.8s）。
> 我方实现：`cmd/protocol-probe`（main.go handle() 主循环）。本文逐帧对照，标出：**[缺失]**（我们从不发送）、**[数据差异]**（发送但内容/形态与官服不同）、**[未应答]**（客户端发了、官服有回应、我们没有）、**[对齐]**（已一致或刻意等价）。
> 语义未定位的帧一律保留并注明「未定位」——不影响收录。
>
> ⚠️ 总前提：本服面向 fork 客户端、以真机实测可用为准；官服（7071/7072/7074 线）方言与 fork 抓包存在已知分叉。凡属「刻意不同」的项（代码注释里有实证记录）在表中注明，不算缺陷。

## 一、登录流程形态差异（宏观）

| 环节 | 官服（c.pcapng 重连） | 我方（protocol-probe） |
|---|---|---|
| 连接后首帧 | （重连场景）客户端直接发 **op04 len=84** 携带会话恢复信息 | 客户端先发 op02 账号登录 → 我方回 0x04 角色列表（main.go:1809）→ 客户端再发 op04 选角（main.go:1857）。首连多一个账号阶段 |
| 会话票据 | op04 后立即回 **op32 len=1026**（"218:#INNER…" 票据；已全解，见 §十二：SoloWorld StoreMsgSave 结构体转储 + 会话密钥回执） | **无 op32**。全仓无 0x20/0x32 服务端帧（internal/transport 仅帧编解码）；客户端无它可正常登录，密钥回执机制已查明可按需镜像 |
| 对钟 | C2S m924（~1s）→ S2C **m294 应答**（回显 client_ms + 玩家 obj + unix 秒 + uptime 天数） | **不答 m924**；改为连接起 1s 周期单方面推 m294（main.go:455），值列格式不同（见 §四-1） |
| 登录握手 | C2S m9（密钥对+版本 11005+MD5，6s 周期，**官服也无逐次应答**） | 不处理=与官服行为一致 **[对齐]** |
| 表下发 | 0x09 属性表（2433 项）→ 0x0A 记录表（**单帧 10429B / 446 schema**） | 0x09（2370 项）→ 0x0A（447 schema 10449B）→ **再发 0x0A 镜像 10429B**（home_records_frame.go，刻意：客户端取其帧头 16B 作 C2S 0x0A 信封头回显） |
| 就绪屏障 | C2S op09 len=1（ClientReady）→ 技能/视图大簇 | 同形：0x09 分支（main.go:2107）**[对齐]** |

### 8.1 S2C 寻址模型修正（重要）

Java 参考服 `CustomMessages.java` 注释与 modern 客户端互证：S2C custom 有**两种互斥寻址**，由首值线型决定——
- 首值 tag2(int) = **数字路由**（引擎 exe 内 ID→handler 表分发，官服抓包主体）；
- 首值 tag6(string) = **命令名路由**（引擎直接调 custom_handler.lua 同名函数，"现代 0x27 壳"）。

## 十二、op32 会话票据全解（2026-11-10 第六轮）

> 样本：c.pcapng（7074 线，2026-11-08）+ artifacts `capture-players/official_login2.pcapng`（7064 线，2026-05）——**仅有的两帧 op32，同为 1026B、布局逐位同构**。提取/解析脚本与样本落盘 `tmp/pcap_analysis/{extract_op32,parse_op32,diff_op32,cmp_op04_op32,scan_artifacts_op32,op32_deep2-5}.py`、`op32_c.bin`、`op32_artifact_official_login2_*.bin`。

### 12.1 定性：不是"票据"，是官服结构体内存转储 + 密钥回执

帧内泄露的服务器源码位置字符串实锤语义：`[SoloWorldStoreMsg.cpp]SoloWorld::StoreMsgSave:199`。op32 = 官服把一个 **1026B 定长 C++ 结构体整体 memcpy 上线**（内含未清零的堆指针、账号名、会话密钥），配合 C2S op04 构成断线重连的会话恢复闭环：

```
+0.000s  C2S op04 len=84  密钥K(10B) + 56×00 + MD5(16B) + 00
+0.060s  S2C op32 len=1026  …@812 内嵌同一密钥K…
```

- **密钥格式恒定**：`905F` + 8 字节随机（两样本一致的前缀；K 客户端在 op04 时已持有 → 来自更早会话的 op32 并本地持久化；本帧为服务端对 K 的回执/再存储）。
- **token 零引用**："18:#INNER" 后的 hex token（43B/49B，解码后首 4 字节恒 `7E 4D 5C 65`）在两样本全流中再无任何帧引用——客户端不回传它。前缀 `N:#NAME` 形态疑为网关内部路由表项（18=路由号，INNER=内网线路），【低置信】猜测。
- 官服网关为 **64 位进程**（帧内含 0x00007ffc70796057 模块指针 + 同簇连续堆指针 0xe174_5781_{d083,d333,d433}；login2 对应 0x7ffc5eb4ca47 / 0xc939_5eb4_6c07）。

## 十三、op14 / op29 / op2A 语义解析（2026-11-10 第六轮，c.pcapng 360 帧逐帧验证）

> 脚本：`tmp/pcap_analysis/{op14_extract,op14_parse,op29_2a_parse,op29_verify,op2a_tvar}.py`。方法：按流序提取三类帧 + 前后邻帧，用 0x09 属性表/0x0A 记录表交叉解码，与后续 0x11/0x18 帧头逐字段配对。

#### 13.1 op14（12B ×225）——记录事务声明帧，布局字节级实证【高】

统一布局 `[14][sub u8][obj u32][owner u32][rec u16]`（无推断成分，225 帧全量验证）：

| sub | obj / owner 含义 | 后续数据帧 | 配对结果 |
|---|---|---|---|
| 00（×127） | 对象域（obj=0x7020fa4 owner=0x3b3cc3 玩家） | **0x11**（单帧行数据）或 **op29**（批量块） | 68 帧直贴 0x11，obj/owner/rec 三字段与 0x11 头**逐位一致**；其余 59 帧贴 op29（同三元组在 op29 载荷 @15 命中） |
| 01（×94） | **视图行域**：obj=view id、owner=行号 objIdx（1 起） | 0x11（视图行附加记录） | 93/94 帧的 (view,行号,rec) 与后续 0x11 头完全一致（如 view1 行1→PropModifyPackRec#394 obj=0x1/owner=0x1） |
| 02（×4） | 全局记录（obj=0 owner=0） | 0x11（WeatherRec#361 等） | 2/4 直贴命中，其余走 op29 |

**定性修正**：op14 不是「确认」而是**先导声明（announce-before-write）**——官服每次写记录前先发 12B 声明三元组，行数据随下一帧到达（载体二选一：0x11 直发 / op29 批量）。对客户端而言是「开始写 X 记录」的事务开界标记。sub1 的 tag 字段=recId（非旧推断的 recAttrIdx）。view45 经脉行 plug_record#419 伴随（§二-D）即此形态。

#### 13.2 op29（×95，41–4187B）——记录批量块载体【中信封/低行内】

信封与 0x47 家族统一：`[29][47][A u32][B u32]`，**A=帧长−1**（95 帧全部吻合）；B 同组恒定、跨组变化（如 Task_Completed 组 22 帧全 B=527），语义未定位（疑逻辑块总长/未压缩长度，B/A≈2–4 有压缩比假象但行头明文可读，排除整体压缩）。

载荷 = `[≤5B 组内续传残余][obj u32][owner u32][rec u16][行数据…]`：58 帧在 @15 精确命中紧前 op14 宣布的三元组；其余 37 帧为多帧组的续传帧（同 B 无声明）。行数据区编码与 0x11 行体不同源（Task_Completed#31 schema=单列 i32，按 0x11 布局 [startRow u16][nRows u16]+行 对不上字节预算），**行级编码未解**。内容按声明记录定名：任务三表（#29/30/31）、FormulaRec、note_wuxue_rec(2750B)、rec_npc_relation(1789B)、卡牌 Origin_Kapai 等——即**大记录的分块批量通道**，与小记录 0x11 直发互补。

#### 13.3 op2A（×16+，261–325B）——装备物品详情帧【高定性/中编码】

同一 0x47 信封。载荷 = 物品属性流（TLV 变体），已解出：

## 十四、0x28 详情帧定版与官服 NPC 物化方言（2026-11-10 第七轮，分支 official-2433-table）

### 14.1 0x28 帧头布局定版（双模板互证）与三轮拒收根因

- 布局：`[0]=0x28` `[1]=0x47 家族标记（固定）` `[2:6]=u32 len-1`（NPC 233=234-1、玩家 3186=3187-1，恒成立）`[6:10]=u32 模板号`（同模板同长同值：290/294/257…，非全局 serial）`[10:13]=0` `[13]=状态位`（0x91 常见；0xc4/0xc8/0x81 见于 0x15x-owner 族）`[14:18]=obj` `[18:22]=owner` `[22:38]=x/y/z/orient 四 f32` `[38:]=记录块`。
- **三轮真机被拒根因**：=1 探针（41d3292/c1cd1b9）把 serial u32 写进 [1:5]——[2:6] len-1 恰好未动，但 **[1]=0x47 家族标记被覆写成 0x01/0x02/0x03**，客户端按错家族解析即报 size/property error（×123 帧/轮）。被拒的是自损帧，不是 0x28 通道本身。
