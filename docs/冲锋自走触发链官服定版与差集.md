## 一、官服自走链定版（对既有认知的三处修正）

### 1.1 触发时序真相：自走是**按下瞬间的本地决策**，受理簇只是兜底

88 次施法逐例对齐 211→首条 m15 state7→受理簇到达（见 tmp/rush_gap 统计）：

| 模式 | 样本 | 时序 |
|---|---|---|
| **按下即走** | 7 例（150.6/267.3/358.1/535.8/572.0/597.1/607.4） | m15 state7 与 211 **同毫秒**，簇 +43ms 后才到 |
| 簇到即走 | ~30 例 | walk_dt ≈ clu_dt ≈ +0.042~0.05s（=RTT；簇到后同拍起走） |
| 延迟起走 | 少数（+0.5~2.4s） | 先前动作未结束（跳跃/出招位移收尾后起走） |
| 不走 | 7 例 | hyjf07 点地族 / 已在射程内直收 |

**结论**：客户端按下时本地判「超射程 + CanRush → 接近」，多数情况毫秒级起走
（预选好目标时）；簇到达是第二武装点。**受理簇字节形态不是本服不自走的
充分解释**——簇四帧官服/本服已逐字节同构（CurSkillID(462)→CurSkillTarget(629)
→m25[30000,skill_pause]→m707[15]，+42ms 状态四连 586[5]/645[1]/646[1]/750[20]）。

### 1.2 走踢帧证伪：0x21(91B 双条目) 是 m15 的**回显应答**，不是驱动指令

32.642 案例：客户端 m15 state7 ×2（双帧起跑，dest=目标 xz、速度 4.5、
intent 0xA0000F01）→ 服务端 **+155ms 回 0x21 len=91 双条目**：obj=玩家
(0x070383e6,0x563e4e)，两入口 dest≈目标位 (947.83,1028.59)（微偏重复）、
slot3=4.689 常量、speed=4.5、orient=-π、尾槽 5.5/9.8、intent=0xA0000F01。
267.3 案例同形（码185）。在途每拍 m15（~2.2s）→ 0x21 len=47 单条目回显
（码219/220）。**官服没有"踢帧"**——rush_cast.go 的 rushWalkKickFrame
（+155ms 主动双入口 0x21 指望驱动客户端走）方向反了：客户端没走时它只是
被当回显吃掉（三轮真机「踢帧被吃但不执行」的真正原因）。echoPlayerMoveIntent
才是正确实现；走踢帧与「时钟对先行」hack 应撤。

### 1.3 选靶 0x28 详情帧证伪

- 30.456 的 0x28(47) 属于**另一个 NPC** obj(0x0700014b,0x150)（monm031300，
  State=walk，posA=(947.9,48.75,992.0)）——发出时间在 0x07 选靶 **前 374ms**，
  与选靶无关（0x28 是官服对移动中 NPC 的 1~2s 节奏周期刷新，全场 279 帧）。
- 官服选靶（0x07 + 431）只回 **416/417 双帧**（LastObject/AutoSelectObject，
  逐字节与我们 writePlayerTargetLocked 同构）。
- **自走目标 0x07018099 全场 1271s 没有收到过任何 0x28/0x1F/0x31**，客户端
  照样自走冲刺——目标 0x28 详情不是接近前提（3de3115 的按需重发假设不成立，
  可撤）。

## 三、真差集（按嫌疑排序）与修复批次

### P0 —— 先取证再动手：采一次本服真机会话

本服症状「客户端零消息」当前只有日志侧证据。分支判断的分水岭：
- 客户端**发了** m15 state7（0xA000 前缀）而模型不动 → 差在**回显/钟对**
  （0x21 回显形态 + m294 钟差）；m15 上一版本实证过会发。
- 客户端**没发** m15 → 差在**本地决策输入**（技能行数据/钟对/物理属性形态）。

用 `NINEYIN_CAPTURE_DIR` tap（capture_dump 逐读写 flush 版）抓一次
登录→选靶→远距按压，c2s 侧判 m15 是否出现。**在此之前不再猜**。

### P1 —— m294 对钟改官服应答方言（低成本，已知影响面）

官服：**应答** C2S m924（1Hz），`[294, 回显client_ms(i64), reqid obj(i64 每答递增),
unix秒(i64), uptime天(f64 常量)]`（44B 定长）。客户端用回显的 client_ms 算
时偏；我们现行自发 `[294, 服务端进程ms, 开机µs, 开机unix, 运行秒]` 值语义
全错位。已知「无钟基准 0x21 位移被吃不执行」——接近段官服全程 1Hz 带钟。
改法：handle m924 → 回 294（回显其值）+ 维持 0x38 应答；撤 scoped 钟对 hack。

### P2 —— 玩家物理属性补官服「登录后 0x10 单属性流」形态

值我们已全带（qinggongMotionProperties 在 0x0D 大档内），但官服是建对象后
~60 条逐帧下发。若引擎接近子系统在属性**变更事件**上武装（默认→5.0 的
更新沿），一次性大档不触发同样路径。改法：sendPlayerSpawn 后补一轮
单属性 0x10 流（官服序：先 ParryRes/HeartSpeed/Rush 族/速度族）。

### P3 —— tryRushArrival 按技能射程分流

六米技（castRange≥5.5，hyjf02 族）官服**全程无 c61**：客户端自走至 ~6.2m
发 220、~5.8m 发 212[尾0] 步行落地。现行 (5.0,6.5] 窗口对六米技发出的 c61
是本服方言（客户端多数无视）。改法：`castRange+1 > 5.0` 的技能在
tryRushArrival 里跳过 c61，只等 212。

### P4 —— 小项

- 落地簇目标模型行：官服 hyjf02 发 **LastNGAttackNpc(idx 871)**，我们发
  LastWGAttackNpc(867)——按技能内外功分流（NG=内功行）。
- rearm 簇序（267.392 官服实证）：`0x12×2 → CurSkillID → CurSkillTarget →
  m25 → PauseSkill=技能 → m707 → 四连`（PauseSkill 在 m25 后、首受理不发
  PauseSkill——32.642 复核确认）；我们 rearm 分支带 CurSkillID=""/msg26/
  PauseSkill="" 前导三帧——与官服 f.pcapng 方言合并核对后统一。
- 撤走踢帧（rushWalkKickFrame + 时钟对先行）与选靶 0x28 重发（证伪清理）。

### 认知修正（记录在案）

- **id 高字节不是类型位**：官服 obj/own 是全局顺序计数器，玩家与 NPC 双族
  混用（技能包玩家=0x070383e6/own 0x563e4e；登录包玩家=0x1105c0e3/own
  0x03defbae；NPC 两种族均出现）。第十八轮「客户端按 id 高位校验类型」的
  解释不成立，NPC 迁 0x07 族无必要。
- 官服接近段玩家在途 0x21 回显逐拍单条目（47B），起跑应答为 91B 双条目
  （双帧起跑→双条目合一帧回显）；我们逐条单条目回显，语义等价待真机验证。

另外确认：NPC 数据本身（0x0D fork 头行+官方位 16-prop、NpcType/CollideRadius 都在）不是自走阻断项——你的“少了 NPC 数据”怀疑可以放下了，矛头指向钟对与玩家属性流的形态，下一步建议直接做 P0 抓包定分水岭，再做 P1。
